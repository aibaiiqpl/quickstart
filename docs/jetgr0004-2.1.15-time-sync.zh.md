## 0. 三句话结论

1. **原文写"与模拟调度服务器同步"是对的**，不用改 —— 调度服务器本身就是那台 NTP 服务器。
2. **东北电力网络没有独立的时刻服务器可换**，实际接続先在非公开的伝送仕様書里。
3. **真正的缺口是判定基准 イ 没有依据文件**，而且改文案绕不过去 —— 必须补一份文件，最小代价是一页别纸（已写好）。

## 1. 先纠正一个前提：同步对象写"调度服务器"是对的

最初的判断是"时刻同步应该走 NTP，所以原文写模拟调度服务器不合逻辑"。查过东北电力网络
官方《出力制御機能付ＰＣＳ等 技術仕様書（高低圧）》后，**这个判断是错的**。

规格书 **7.8 节（与调度服务器的数据授受）** 明确规定，调度服务器自身就提供 NTP 服务器功能：

| 可获取的数据 | 装置侧的请求 |
|--------------|--------------|
| 时刻信息（NTP 服务器） | 对时（NTP 客户端） |

**6.3 节（时刻设定）** 规定"须与电力服务器或配信事业者服务器的时钟信息同步"，并附带
以下要求：

| 项目 | 要求 |
|------|------|
| 时钟篡改对策 | 时刻设定须通过 NTP 服务器或 GPS 等同步，或由厂商服务人员实施；投运后手动调时限制在**每日 ±10 分钟以内**（初始设定除外） |
| 时钟丢失对策 | 停电时内部时钟不得丢失；若时钟（含年月日）丢失，**须停止发电设备**直至完成时刻同步或人工重设 |
| 时钟精度 | 内部时钟与晶振时钟等同步，**误差 ±60 秒以内／月（常温）**；固定调度更新（每年至少 1 次）时校正时刻以维持该精度 |

规格书的解说部分给出了理由：出力制御调度以 30 分钟为单位指定控制值，内部时刻偏差或
时刻篡改的影响非常大，因此原则上要求与服务器进行时刻同步。

**结论**：成绩书原文"与模拟调度服务器同步"与规格书一致。**"走 NTP"和"与调度服务器同步"
并不矛盾** —— 调度服务器就是那台 NTP 服务器，装置以 NTP 客户端身份向它对时。所以**不能**
把记载简单替换成"NTP 服务器"，而应把两者的关系写明。

另外：**东北电力网络不存在 `re-ene-time.*` 这种独立的时刻配信服务器**（北海道电力的
`re-ene-time.hepco.co.jp` 是该公司专有的）。实际接続先按规格书 7.7 节的规定，在**另行制定的
伝送仕様書**中指定（非公开，发给受审厂商）。你们 `~/power-control/docs/` 下有那份
《出力制御機能付PCS等（高低圧）スケジュール情報配信システム伝送仕様書（2023.06.21）》，
但是扫描件，无法抽取文字，接続先要人工翻阅确认。

**⚠️ 待确认**：邮件提到 1250kW，据此推断为高压并网（适用高低圧版规格书），但并网区分是
按**受电电压**决定的，需确认适用的是"高低圧"还是"特別高圧"版。若适用特別高圧版，则要求
只有一句 —— 不指定同步对象，时刻源由厂商选择：**"厂商侧的出力制御装置等应适时与日本标准时
对时，时钟精度须在 ±60 秒以内／月"**。

## 2. 原文真正的问题

问题不在同步对象，而在**试验结果栏没有写成能满足判定基准的内容**。

1. **判定基准 イ 的依据文件不存在。** 判定基准 イ 要求"同步所需时间须在技术规格书等中
   明确记载"，这里指的是**厂商侧的文件** —— 东北电力网络的规格书里**没有**同步耗时的规定，
   规定它是厂商的责任。但我方并没有含该记载的文件，所以原文"确认技术规格书中有明确记载"
   是无据的。审查方要求提交规格书正是因为这一点；**不补出文件，这一项就无法判定为合格**
   （见第 3 节）。
2. **判定基准 ロ 缺定量根据。** 只说"装置时刻正常同步"，没有给出同步后装置时刻与服务器
   时刻的偏差、以及同步所需时间，无法特定"通过日志确认了什么"。
3. **同步方式表述不清**，读不出规格书 7.8 节所定的"调度服务器的 NTP 服务器功能 ← 装置的
   NTP 客户端"这一结构。

## 3. 判定基准 イ 的依据文件 —— 附一页别纸

**这一条不能靠改文案绕过。** 判定基准 イ 要求"同步所需时间须在技术规格书**等**中明确记载"，
只要没有任何文件写明同步耗时，成绩书写成什么样都无法判定为合格 —— 审查方要的就是那个
"明确记载"的载体。

但条文写的是"技术规格书**等**"，不是"技术规格书"。所以**不需要**正式的技术规格书：
使用说明书、订货规格书、装置规格一览，或者**成绩书附的一页别纸**，都可以作为依据。

我方目前没有含该记载的规格书，因此采用**在成绩书上附一页别纸**的方式。别纸已写好：

- 提交用日文原稿：[jetgr0004-2.1.15-annex-time-sync-spec.md](jetgr0004-2.1.15-annex-time-sync-spec.md)
- 中文对照 + 填写要领：[jetgr0004-2.1.15-annex-time-sync-spec.zh.md](jetgr0004-2.1.15-annex-time-sync-spec.zh.md)

别纸共 11 项，与要件的对应关系：

| 项 | 内容 | 对应要件 |
|----|------|----------|
| 2 | 时刻同步方式（NTP 客户端，无手动设定功能） | 东北电力规格书 6.3 时钟篡改对策 |
| 3 | 同步对象（调度服务器的 NTP 服务器功能） | 东北电力规格书 6.3、7.8 |
| 4 | 同步触发（启动时／每小时／取得调度时） | — |
| **5** | **同步耗时 60 秒以内** | **判定基准 イ（核心）** |
| 6 | 同步后时刻精度 ±1 秒以内 | 判定基准 ロ 的定量根据 |
| 7 | 内部时钟精度 ±60 秒／月、停电保持、定期校正 | 东北电力规格书 6.3 时钟精度 |
| 8 | 时刻篡改对策（无手动调时功能） | 东北电力规格书 6.3 |
| 9 | 时钟丢失时停止发电设备 | 东北电力规格书 6.3 时钟丢失对策 |
| 11 | 日志记录内容 | 判定基准 ロ |

填写要领和两处对外承诺风险（第 8、9 项），见別纸中文版末尾。

### 试验结果（【試験結果】栏）—— 主要改写部分

| | 改法 |
|---|---|
| イ | 依据从"技术规格书第○章○节"改为**"别纸○《时刻同步功能 规格》第 5 项"**，并写出规定值本身（60 秒以内），而不是只说"确认有记载" |
| ロ | 改为列出实测数据表：同步对象、同步前偏差、同步耗时、同步后偏差、判定 |

实测数据表（**这些是参考值，成绩书必须换成实机数据**）：

| 确认项目 | 实测值 |
|----------|--------|
| 同步对象 | 模拟调度服务器（NTP 服务器功能，stratum 1） |
| 同步前的时刻偏差 | 58,348,100.6 秒（约 675 天） |
| 同步所需时间 | **0.98 秒** |
| 同步后的时刻偏差 | **-0.021 秒** |
| 判定 | 规定值 60 秒以内、时刻精度 ±1 秒以内均满足 |

结论句的逻辑：同步前存在含年月日的巨大误差，同步后已校正到相对服务器 ±1 秒以内 →
确认含年月日正确同步 → 同步耗时满足规格书规定值 → 本项判定为合格。

**✎ 待填写**：上表实测值是在开发机（Ubuntu 24.04 / systemd-timesyncd）上、对公开 NTP

不是对模拟调度服务器测的。成绩书必须换成**实机对模拟调度服务器取得的值**。

## 5. 审查意见 (2) 回复要点

日文原稿见 [jetgr0004-2.1.15-time-sync.md](jetgr0004-2.1.15-time-sync.md) 第 5 节。
要说的三件事：

1. **说明同步方式**：本装置的时刻同步按贵社技术规格书（高低圧）7.8 节的规定，采用装置以
   NTP 客户端身份向调度服务器提供的 NTP 服务器功能同步的方式实现 —— 顺手把"为什么原文
   写调度服务器是对的"也交代了。
2. **交出判定基准 イ 的依据**：已整备《时刻同步功能 规格》别纸并随回复附上，同步耗时在
   该别纸第 5 项规定为 60 秒以内。
3. **说明试验结果栏的改订**：改为明记实测值 —— 从把装置时刻设为含年月日错误值的状态开始，
   用装置日志实测同步耗时和同步后偏差，耗时在规定值 60 秒以内、同步后偏差在 ±1 秒以内。

## 6. 实机验证步骤

```bash
# 指定模拟调度服务器（NTP 服务器功能）为同步对象执行
# 第2个参数＝要故意设错的时刻（年月日也要与当前不同），第3个参数＝规定值［秒］
sudo ./scripts/test_time_sync.sh <模拟调度服务器地址> "2024-11-05 03:27:11" 60

# 需要指定同步机构时
sudo FORCE_METHOD=chrony ./scripts/test_time_sync.sh <地址> "2024-11-05 03:27:11" 60
```

脚本无论成败都会通过 EXIT trap 恢复装置时刻。证据留在 syslog（tag
`hulk-powerflow-limitation`）和标准输出末尾的 JSON 行。

## 7. 测量注意事项 —— 这几条直接决定数据可不可信

- **测试期间会停掉常驻 NTP 守护进程。** 不停的话，无法特定"把时钟改回来的是被测对象还是
  后台守护"，测出的耗时没有意义。
- **用 systemd-timesyncd 的装置，不要把启动瞬间的时钟跳变当成同步完成。** timesyncd 启动时
  会先把时钟恢复成本地 clock 文件的 mtime，测这个动作会得到一个与 NTP 无关的极短时间。
  实测撞到过：显示 0.78 秒"完成"，而同步后残差 4.09 秒 —— 按这个数写进成绩书是要出事的。
  脚本把它单独记为 `First movement`，以 NTP 确认同步后的时刻作为耗时。
- **同步后的偏差不靠被测工具的返回码，而用独立的只读 SNTP 查询实测。** 这才是判定基准 ロ
  的定量根据。
- **同步对象有多个 A 记录时要逐个探测。** `re-ene-time.hepco.co.jp` 的两个地址里，实测有
  一个会超时；只看第一个会把"其实能连通"误判成失败。
