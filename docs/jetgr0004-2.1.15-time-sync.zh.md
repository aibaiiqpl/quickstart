## 0. 三句话结论

1. **时刻同步对象是独立的"时刻服务器"，不是调度服务器** —— 伝送仕様書 第 5 章把两者
   明确拆开。但 JET 的判定基准 ロ 写的是"模拟调度服务器"，这是因为试验环境里由模拟调度
   服务器兼任时刻服务器角色，两者不矛盾，成绩书把这层关系写明即可。
2. **东北电力网络没有 `re-ene-time.*` 那种专用时刻服务器**，实际 NTP 接続先在非公开的
   伝送仕様書里。你们手上那份是**関西電力送配電版（秘密文書）**，指定值为 `ntp.nict.jp:123`，
   东北电力版需个别申请获取后核对。
3. **真正的缺口是判定基准 イ 没有依据文件**，而且改文案绕不过去。电力公司的任何文档里
   都没有"同步所需时间"这个数（这是装置性能特性，只有厂商能申报）—— 必须补一份文件，
   最小代价是一页别纸（已写好）。

## 1. 时刻同步对象：独立的时刻服务器，不是调度服务器

东北电力网络《出力制御機能付ＰＣＳ等 技術仕様書（高低圧）》**7.8 节**把"时刻信息
（NTP 服务器）"列为从调度信息配信系统可获取的数据之一：

| 可获取的数据 | 装置侧的请求 |
|--------------|--------------|
| 时刻信息（NTP 服务器） | 对时（NTP 客户端） |

只读这一条，容易理解成调度服务器自身就是时刻源。但 **7.7 节**规定"装置与电力服务器的
通信在另行制定的伝送仕様書中指定"，而伝送仕様書第 5 章「时刻同期」把结构写得很清楚：

| 节 | 规定内容 |
|----|----------|
| 5.1 时刻同步概要 | 时刻同步在**时刻服务器**与发电所之间用 NTP 进行（图5.1 里时刻服务器与发电所是两个独立节点） |
| 5.2 时刻同步协议 | 通信协议 NTP；同步方法 **Step 模式**；指定 NTP 服务器的 FQDN 与端口（123） |
| 5.3 时刻同步时机 | 4 种触发（首次通信 ID 认证前／电源启动时／**定期更新 最多 1 次/日**／其他手动更新）；定期更新的实施时间段为给时刻服务器分散负载，按发电所 ID 末尾校验和分配；出错时 **1 分间隔最多重试 5 次**，之后 30 分钟后继续再重试 |

所以装置的同步对象是 **NTP 时刻服务器**。而 JET 的判定基准 ロ 写的是"与模拟调度服务器的
时刻信息同步" —— 这指的是**试验环境中由模拟调度服务器兼任时刻服务器（NTP 服务器功能）
的角色**。两者不矛盾：装置向伝送仕様書指定的 NTP 服务器同步，试验时这个角色由模拟服务器
扮演。成绩书把这层关系写明即可。

另外：**东北电力网络不存在 `re-ene-time.*` 这种专用时刻配信服务器**（北海道电力的
`re-ene-time.hepco.co.jp` 是该公司专有的）。

### 1.1 ⚠️ 重要待确认 —— 伝送仕様書的版本

你们 `~/power-control/docs/` 下那份伝送仕様書是 **関西電力送配電株式会社版，盖着「秘密文書」**。
上表的结构和数值来自该版本（NTP 服务器指定为 `ntp.nict.jp`，端口 123）。给东北电力提交前必须：

1. **取得东北电力网络版的伝送仕様書**，核对 NTP 服务器指定值（FQDN／端口）、同步时机、
   重试条件。东北电力**不公开**该文档，需个别申请或询问获取。
2. **不要把関西電力送配電版引用或附在给东北电力的提交物里** —— 既是秘密文書，拿别家
   公司的规定当依据提交也不合适。
3. 别纸（第 3 节）的第 3、4、10 项要按上述核对结果最终确定。

顺带一个交叉验证：脚本默认的 `ntp.nict.jp` 正好就是関西版伝送仕様書指定的值 —— 当初选它
的理由只是"日本标准时的公开服务器"，结果与规格书一致。

### 1.2 技术规格书 6.3 节的相关要求

时刻同步的配套要求在 6.3 节，别纸要与之保持一致：

| 项目 | 要求 |
|------|------|
| 时钟篡改对策 | 时刻设定须通过 NTP 服务器或 GPS 等同步，或由厂商服务人员实施；投运后手动调时限制在**每日 ±10 分钟以内**（初始设定除外） |
| 时钟丢失对策 | 停电时内部时钟不得丢失；若时钟（含年月日）丢失，**须停止发电设备**直至完成时刻同步或人工重设 |
| 时钟精度 | 内部时钟与晶振时钟等同步，**误差 ±60 秒以内／月（常温）**；固定调度更新（每年至少 1 次）时校正时刻以维持该精度 |

规格书解说给出的理由：出力制御调度以 30 分钟为单位指定控制值，内部时刻偏差或时刻篡改的
影响非常大，因此原则上要求与服务器进行时刻同步。

**⚠️ 待确认**：邮件提到 1250kW，据此推断为高压并网（适用高低圧版规格书），但并网区分是
按**受电电压**决定的，需确认适用的是"高低圧"还是"特別高圧"版。若适用特別高圧版，则要求
只有一句 —— 不指定同步对象，时刻源由厂商选择：**"厂商侧的出力制御装置等应适时与日本标准时
对时，时钟精度须在 ±60 秒以内／月"**。

## 2. 原文真正的问题

问题不在同步对象，而在**试验结果栏没有写成能满足判定基准的内容**。

1. **判定基准 イ 的依据文件不存在。** 判定基准 イ 要求"同步所需时间须在技术规格书等中
   明确记载"，这里指的是**厂商侧的文件**。已逐一查证：东北电力技術仕様書（高低圧／特別高圧）
   和伝送仕様書（関西版）里**都没有**同步耗时的规定 —— 那里有的是时钟精度 ±60 秒/月、
   手动调时 ±10 分/日、重试 1 分×5 次/30 分，都是别的量。同步耗时是装置性能特性，
   只有厂商能申报。但我方并没有含该记载的文件，所以原文"确认技术规格书中有明确记载"
   是无据的。审查方要求提交规格书正是因为这一点；**不补出文件，这一项就无法判定为合格**
   （见第 3 节）。
2. **判定基准 ロ 缺定量根据。** 只说"装置时刻正常同步"，没有给出同步后装置时刻与服务器
   时刻的偏差、以及同步所需时间，无法特定"通过日志确认了什么"。
3. **同步方式表述不清**，读不出"装置作为 NTP 客户端向时刻服务器（试验环境中由模拟调度
   服务器兼任）以 Step 模式同步"这一结构。

## 3. 判定基准 イ 的依据文件 —— 附一页别纸

**这一条不能靠改文案绕过。** 判定基准 イ 要求"同步所需时间须在技术规格书**等**中明确记载"，
只要没有任何文件写明同步耗时，成绩书写成什么样都无法判定为合格 —— 审查方要的就是那个
"明确记载"的载体。

但条文写的是"技术规格书**等**"，不是"技术规格书"。所以**不需要**正式的技术规格书：
使用说明书、订货规格书、装置规格一览，或者**成绩书附的一页别纸**，都可以作为依据。

我方目前没有含该记载的规格书，因此采用**在成绩书上附一页别纸**的方式。别纸已写好：

- 提交用日文原稿：[jetgr0004-2.1.15-annex-time-sync-spec.md](jetgr0004-2.1.15-annex-time-sync-spec.md)
- 中文对照 + 填写要领：[jetgr0004-2.1.15-annex-time-sync-spec.zh.md](jetgr0004-2.1.15-annex-time-sync-spec.zh.md)

别纸共 11 项，与要件的对应关系：

| 项 | 内容 | 对应要件 |
|----|------|----------|
| 2 | 时刻同步方式（NTP 客户端、Step 模式、无手动设定功能） | 技術仕様書 6.3、伝送仕様書 5.2 |
| 3 | 同步对象（伝送仕様書指定的时刻服务器） | 伝送仕様書 5.1／5.2 |
| 4 | 同步触发（4 种，定期更新最多 1 次/日 + 分配时间段） | 伝送仕様書 5.3 表5.3／5.4 |
| **5** | **同步耗时 60 秒以内** | **判定基准 イ（核心）** |
| 6 | 同步后时刻精度 ±1 秒以内 | 判定基准 ロ 的定量根据 |
| 7 | 内部时钟精度 ±60 秒／月、停电保持、定期校正 | 东北电力规格书 6.3 时钟精度 |
| 8 | 时刻篡改对策（无手动调时功能） | 东北电力规格书 6.3 |
| 9 | 时钟丢失时停止发电设备 | 东北电力规格书 6.3 时钟丢失对策 |
| 10 | 重试条件（1 分×最多 5 次 → 30 分后继续） | 伝送仕様書 5.3 注※ |
| 11 | 日志记录内容 | 判定基准 ロ |

填写要领和两处对外承诺风险（第 8、9 项），见別纸中文版末尾。

## 4. 成绩书 2.1.15 改写要点

日文原稿见 [jetgr0004-2.1.15-time-sync.md](jetgr0004-2.1.15-time-sync.md) 第 4 节，
直接复制即可。改动要点如下。

### 确认方法（【確認方法】栏）

| | 改动 |
|---|---|
| イ | 明确"确认什么" —— 同步方式、同步对象、同步触发、同步耗时的规定值 |
| ロ | **不变**（把装置时刻设为与当前不同的值，年月日也要不同） |
| ハ | 补上要测量的量 —— 与模拟调度服务器（NTP 服务器功能）同步，并通过装置日志确认同步耗时、以及同步后装置时刻与服务器时刻的偏差 |

### 判定基准（【判定基準】栏）

**完全不动**，沿用原文。这是 JET 定的，不能改。

### 试验结果（【試験結果】栏）—— 主要改写部分

| | 改法 |
|---|---|
| イ | 依据从"技术规格书第○章○节"改为**"别纸○《时刻同步功能 规格》第 5 项"**，并写出规定值本身（60 秒以内），而不是只说"确认有记载" |
| ロ | 改为列出实测数据表：同步对象、同步前偏差、同步耗时、同步后偏差、判定 |

实测数据表（**这些是参考值，成绩书必须换成实机数据**）：

| 确认项目 | 实测值 |
|----------|--------|
| 同步对象 | 模拟调度服务器（兼任时刻服务器＝NTP 服务器功能，stratum 1） |
| 同步前的时刻偏差 | 58,348,100.6 秒（约 675 天） |
| 同步所需时间 | **0.98 秒** |
| 同步后的时刻偏差 | **-0.021 秒** |
| 判定 | 规定值 60 秒以内、时刻精度 ±1 秒以内均满足 |

结论句的逻辑：同步前存在含年月日的巨大误差，同步后已校正到相对服务器 ±1 秒以内 →
确认含年月日正确同步 → 同步耗时满足规格书规定值 → 本项判定为合格。

**✎ 待填写**：上表实测值是在开发机（Ubuntu 24.04 / systemd-timesyncd）上、对公开 NTP
服务器（`ntp.nict.jp`、`re-ene-time.hepco.co.jp`，均为 stratum 1）测得的**参考值**，
不是对模拟调度服务器测的。成绩书必须换成**实机对模拟调度服务器取得的值**。

## 5. 审查意见 (2) 回复要点

日文原稿见 [jetgr0004-2.1.15-time-sync.md](jetgr0004-2.1.15-time-sync.md) 第 5 节。
要说的三件事：

1. **说明同步方式**：本装置的时刻同步按贵社技术规格书（高低圧）7.8 节的规定，采用装置以
   NTP 客户端身份向调度服务器提供的 NTP 服务器功能同步的方式实现 —— 顺手把"为什么原文
   写调度服务器是对的"也交代了。
2. **交出判定基准 イ 的依据**：已整备《时刻同步功能 规格》别纸并随回复附上，同步耗时在
   该别纸第 5 项规定为 60 秒以内。
3. **说明试验结果栏的改订**：改为明记实测值 —— 从把装置时刻设为含年月日错误值的状态开始，
   用装置日志实测同步耗时和同步后偏差，耗时在规定值 60 秒以内、同步后偏差在 ±1 秒以内。

## 6. 实机验证步骤

```bash
# 指定模拟调度服务器（NTP 服务器功能）为同步对象执行
# 第2个参数＝要故意设错的时刻（年月日也要与当前不同），第3个参数＝规定值［秒］
sudo ./scripts/test_time_sync.sh <模拟调度服务器地址> "2024-11-05 03:27:11" 60

# 需要指定同步机构时
sudo FORCE_METHOD=chrony ./scripts/test_time_sync.sh <地址> "2024-11-05 03:27:11" 60
```

脚本无论成败都会通过 EXIT trap 恢复装置时刻。证据留在 syslog（tag
`hulk-powerflow-limitation`）和标准输出末尾的 JSON 行。

## 7. 测量注意事项 —— 这几条直接决定数据可不可信

- **测试期间会停掉常驻 NTP 守护进程。** 不停的话，无法特定"把时钟改回来的是被测对象还是
  后台守护"，测出的耗时没有意义。
- **用 systemd-timesyncd 的装置，不要把启动瞬间的时钟跳变当成同步完成。** timesyncd 启动时
  会先把时钟恢复成本地 clock 文件的 mtime，测这个动作会得到一个与 NTP 无关的极短时间。
  实测撞到过：显示 0.78 秒"完成"，而同步后残差 4.09 秒 —— 按这个数写进成绩书是要出事的。
  脚本把它单独记为 `First movement`，以 NTP 确认同步后的时刻作为耗时。
- **同步后的偏差不靠被测工具的返回码，而用独立的只读 SNTP 查询实测。** 这才是判定基准 ロ
  的定量根据。
- **同步对象有多个 A 记录时要逐个探测。** `re-ene-time.hepco.co.jp` 的两个地址里，实测有
  一个会超时；只看第一个会把"其实能连通"误判成失败。
